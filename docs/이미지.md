# 이미지 속 일본어

이 게임은 대부분의 글자를 12×12 폰트로 그리지만, **그림으로 박아 놓은 일본어**도
두 종류 있습니다. 폰트만 한글로 바꿔서는 이들이 일본어로 남습니다.

| 종류 | 개수 | 위치 |
|---|---|---|
| 타이틀 로고 `信長の野望` | 1 | BG0 8bpp, ROM `0x08002C` / `0x0595F0` |
| UI 라벨 스프라이트 (커맨드 버튼·합전 명령·무장 능력치·상태창 등) | **103** | OBJ 4bpp, ROM `0x153400` / `0x233A24` / `0x237704` / `0x239264` / `0x23A2E4` / `0x23AD04` |

> 이전 판(v2.1)의 이 문서에는 "이미지에 박힌 일본어는 타이틀 로고 하나뿐"이라고
> 적혀 있었습니다. **틀린 서술이었습니다.** 그때는 다이묘 선택 화면까지밖에
> 확인하지 못했고, 본편 화면에 들어가서야 커맨드 버튼과 상태창 항목명이
> 전부 그림이라는 것을 알았습니다.

## 어떻게 찾았나

### 1) 화면을 그대로 가져오기

정적 분석만으로는 그래픽 위치를 특정하지 못했습니다. 4bpp 타일로 렌더해 봐도
타일셋은 타일맵 없이는 조립되지 않고, 폭 자동 검출도 뚜렷한 값이 나오지 않았습니다.

그래서 mGBA 의 GDB 서버에 붙어 VRAM(96KB)·팔레트·OAM·IO 를 덤프하고,
`DISPCNT`·`BGnCNT` 를 해석해 화면을 재구성한 뒤, 화면에 쓰인 타일 바이트를
**ROM 에서 역검색**해 원본 위치를 확정했습니다. (`analysis/grab.py`, `analysis/ui_map.py`)

키 입력은 UI 조작 없이 넣었습니다. 키 처리 루틴을 찾아

```asm
08002482: ldr  r0, [pc, #0x1c]   ; 0x04000130 (KEYINPUT)
08002484: ldrh r1, [r0]
08002486: mvns r1, r1            ; GBA 키는 active-low
08002494: bics r0, r2            ; 새로 눌린 키 = 현재 & ~직전
08002496: strh r0, [r4]          ; [0x03001478] 새로 눌림
08002498: strh r1, [r3]          ; [0x03001470] 현재
```

루틴이 끝나는 지점에 브레이크포인트를 걸고, 멈출 때마다 두 변수에 원하는 키를
써 넣어 게임을 진행시켰습니다. (`analysis/drive.py`)

### 2) 라벨 스프라이트를 롬 전체에서 훑기

한 화면에서 찾은 버튼 하나의 주소를 기준으로 삼아, **라벨의 생김새 자체**를
조건으로 롬 전체를 4바이트 간격으로 훑었습니다. (`analysis/label_find.py`)

- 위·아래·왼쪽·오른쪽 테두리가 각각 한 색
- 안쪽에 3색 이상 (빈 판이 아님)
- 오른쪽 끝이 투명하면 그만큼 폭을 줄여 다시 판정 (28px·24px 라벨)

이렇게 폭 16/24/32/64px 라벨을 전부 찾아, 배열마다 일정한 stride(대개 `0x120`)로
이어져 있다는 것까지 확인했습니다.

## 타이틀 로고 교체

### 원본 구조

| 항목 | 값 |
|---|---|
| 레이어 | BG0, **8bpp**(256색), 우선순위 3 |
| 타일 데이터 | VRAM `0x4000` ← ROM **`0x08002C`** (타일 0~203)<br>VRAM `0x7300` ← ROM **`0x0595F0`** (타일 204~) |
| 화면 맵 | VRAM `0xE000`, 30×20 칸 |
| 압축 | **없음** (ROM 바이트가 VRAM 과 그대로 일치) |
| 글자 색 | 크림 면 `(248,248,192)` / 빨강 외곽 `(248,0,0)` / 어두운 그림자 |
| 글자 영역 | x 17~221, y 35~93 (205×59px) |

로고는 별도 스프라이트가 아니라 **불꽃 배경 그림에 통째로 그려져** 있습니다.

### 작업

1. **글자 픽셀 검출** — 크림 계열 + 채도 높은 빨강.
   팔레트 인덱스만 보면 어두운 외곽선을 놓쳐 획이 남으므로 RGB 조건도 함께 씁니다.
2. **배경 복원** — 검출 영역을 주변 배경에서 반복 확산으로 메웁니다(60회).
   불꽃 그라데이션이라 자연스럽게 이어집니다.
3. **한글 그리기** — 원본과 같은 3겹 구조로 그립니다.
   그림자(우하 3px) → 빨강 외곽(2px) → 크림 면
4. **8bpp 인덱스화** — 원본 팔레트에서 가장 가까운 색을 찾습니다.
   팔레트와 타일맵은 건드리지 않습니다.
5. **타일 기록** — 화면 30×20 칸을 타일 단위로 되돌려 해당 ROM 오프셋에 씁니다.

### 글자 크기

원문 `信長の野望` 은 5자가 205px, **자당 약 41px** 입니다.
`노부나가의 야망` 7자를 한 줄에 넣으면 자당 29px 로 작아지므로,
**두 줄로 나눠 자당 41px 을 지켰습니다.**

```
노부나가의
   야망
```

### 공유 타일 처리

같은 타일을 여러 칸이 쓰는 경우가 37개 있었습니다.
'글자를 지운 새 내용'과 '원래 그대로'가 충돌하는데, 그냥 건너뛰면 지워야 할 획이
화면에 남습니다. 그래서 **원본과 가장 많이 다른 쪽(= 글자를 지운 결과)** 을 채택합니다.
배경 무늬는 어디서 쓰이든 같은 그림이라 이렇게 해도 안전합니다.

### 색 구조

- **배경** — 세로 그라데이션을 2색 체커 디더로 표현합니다. 색은 `y` 와 `(x+y)&1` 로 정해집니다.
- **글자** — 어두운 획색 A + 오른쪽아래 1px 하이라이트 B (음각 효과).
- A/B 와 배경색은 계열(내정·군사·외교·상태창…)마다 다릅니다.

### 빈 판 복원 — 여기가 어려웠다

한글을 넣으려면 먼저 원래 글자를 지운 **빈 판**이 필요합니다.
그런데 12px 한자는 획이 촘촘해서 **한 줄 안에서 획 픽셀이 배경보다 많은 경우가
흔합니다.** 그래서 "픽셀별 최빈값"으로는 글자가 지워지지 않고 그대로 남습니다.

세 단계로 풀었습니다.

1. **후보 좁히기** — 테두리 쪽에 한 번이라도 쓰인 색만 배경 후보로 둡니다.
2. **2단 투표** — 라벨마다 그 줄(같은 패리티)의 최빈 후보색을 먼저 뽑고,
   그 결과를 같은 계열 라벨 전체로 다시 다수결합니다.
   획은 글자마다 자리가 달라 2차에서 밀리고 배경만 살아남습니다.
3. **색 사다리 보정** — 배경은 위에서 아래로 이어지는 색 사다리입니다.
   여러 줄에 걸쳐 나오는 색만 사다리로 인정하고, 한두 칸에서만 튀는 색
   (대개 하이라이트)은 사다리 안에서 다시 뽑습니다.

폭이 다른 라벨(24/32/64px)도 x 원점과 디더 위상이 같아 **한 계열로 묶어**
표본을 늘렸습니다. 액자형 라벨 32장이 한 통이 되어 표가 깨끗하게 나옵니다.

### 한글 넣기

- 원본 글자가 차지하던 사각 영역을 재서 그 안에 가운데 맞춤으로 넣습니다.
- 칸 폭에 맞춰 **갈무리11 → 갈무리11 Condensed → 자간 0** 순으로 자동 선택합니다.
  (24px 판은 Condensed, 32px 판은 일반이 들어갑니다)
- 획색 A 로 글자를, 오른쪽아래 1px 에 하이라이트 B 를 찍어 원본의 음각 느낌을 유지합니다.

### 번역 원칙

- 메뉴는 **띄어쓰기 없이** 2글자로 맞춰 가독성을 확보했습니다.
- 한자 약자로 축약된 항목은 무리하게 풀지 않고 그 수준으로 옮겼습니다.
  (`兵忠`→`병충`, `民忠`→`민충`, `城防`→`성방`, `石高`→`석고`)
- 고유명사 성격의 관직·신분은 일본어 읽기를 씁니다. (`大名`→`다이묘`)

## 아직 남은 것

### 지도 화면 상단 상태창 — 해결

`金 米 兵数 / 石高 治水 商業 / 技術 城防 鉄砲` 는 **다른 배열**에 따로 있었습니다.

처음에는 `0x239264` · `0x23A2E4` 에 같은 글자(金·石高·技術…)의 액자형 판이 있어서
그것이 상태창 라벨이라고 판단했다가 틀렸습니다. 대조 기준이 문제였습니다.

| 기준 | 결과 |
|---|---|
| 흰 글자 픽셀의 배치만 비교 | 486/512 일치 → "같다" (잘못된 결론) |
| 팔레트 없이 색 ↔ 인덱스 일대일 대응 | 384칸 중 **147칸 불일치** → 다른 그림 |

첫 기준은 배경이 전부 '흰색 아님'으로 뭉뚱그려져 실제보다 훨씬 후하게 나옵니다.

### 어떻게 찾았나 — 일대일 대응 판정

`analysis/tile_bij.py` 는 화면 8×8 조각을 롬에서 찾되, 다음 두 조건만 봅니다.

    (a) 모든 자리 i 에서  T[i] == T[대표자리(색_i)]      같은 색 → 같은 인덱스
    (b) 색마다의 대표 인덱스가 서로 전부 다르다          다른 색 → 다른 인덱스

조건이 둘뿐이라 벡터 연산으로 롬 전체를 몇 초에 훑습니다. 화면 (88,16) 한 칸을
넣으니 롬 전체에서 **`0x23AD24` 단 하나**가 나왔습니다.

거기서부터 이웃 칸들을 같은 방법으로 확인해 배치를 역산했습니다.

- 가로 이웃 간격 `0x20` (타일 1개), 세로 이웃 간격 `0x60` (타일 3개)
- → 한 줄에 타일 3개 = **폭 24px 스프라이트**
- 라벨 간 간격 `0xE0` (타일 7개 = 그림 6타일 + 여분 1타일)

### 이 판의 만듦새

액자형과 다릅니다.

| 항목 | 내용 |
|---|---|
| 폭 | 24px 중 왼쪽 2px 는 투명, 그려지는 곳은 x=2~23 |
| 배경 | 디더 **없이** 줄마다 단색인 세로 그라데이션 (`1356 78A9 9A87 6531`) |
| 글자 | 흰 획(인덱스 2) + 1px 외곽선 |
| 외곽선 색 | 그 줄 배경의 그림자색 — 줄마다 다르다 (`13BCCDDDDDDCC531`) |

배경을 되살릴 때, 폭이 22px 뿐이라 획 픽셀이 배경보다 많은 줄이 흔했습니다.
최빈값도 '가장 긴 연속 구간'도 획에 밀려서, **글자가 거의 닿지 않는 양끝 두 칸만
보고 14장으로 다수결**하는 방식으로 해결했습니다. (`技術` 처럼 끝까지 닿는 글자가
몇 개 있어도 다수는 배경이라 흔들리지 않습니다)
