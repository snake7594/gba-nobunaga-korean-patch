# 작업 과정

폰트 탐색부터 패치 완성까지의 전체 파이프라인입니다.

---

## 0. 사전 실험 — 독음 패치로 가능성 검증

본격 번역에 앞서, **한자 글리프를 한국어 독음 한 글자로 바꾸기만** 해 보았습니다.
한자 1자 = 한글 1음절이라 1:1 치환이 되고, 텍스트를 전혀 건드리지 않아도
`織田信長` 이 `직전신장` 으로 보입니다.

이 실험으로 두 가지를 확인했습니다.

1. 폰트 주소와 매핑 테이블 해석이 정확하다
2. 갈무리11 12px 한글이 이 게임 화면에서 읽을 만하다

검증이 끝난 뒤 독음 패치는 폐기하고 정식 번역으로 넘어갔습니다.

---

## 1. 텍스트 추출

```
master_extract2.py → master_strings.json (7,419개)
```

- 매핑 테이블에 있는 1,869자만 유효 문자로 인정해 오검출을 줄임
- 널 종단 파싱, 가이지는 `{G00}` 토큰화
- 롬 전역에서 4바이트 정렬 워드를 훑어 `0x08xxxxxx` 포인터를 찾고,
  그 대상이 유효 문자열이면 `ptr` 로 분류
- 각 문자열의 **뒤따르는 0 바이트 수(slack)** 를 함께 기록 → 제자리 확장 여유

## 2. 번역 단위 구성

```
build_units2.py → units2.json
```

- ASCII가 섞인 `field` 엔트리 273개는 노이즈로 판단해 제외
- 포인터 주소가 4씩 연속하는 런을 찾아 **시퀀스 187그룹** 복원
  (한 문장이 여러 조각으로 쪼개진 경우를 함께 번역하기 위함)
- 한자로만 이루어진 DB 필드 4,391개는 **독음 자동 변환**으로 처리
  (`eumdok.py` 의 한자 1,624자 독음표 + 두음법칙)
- 나머지 1,035개 solo + 187 시퀀스를 실제 번역 대상으로 분리

## 3. 번역

```
build_batches.py → tr_batches/batch_000..052.json + glossary.json
        ↓  (배치별 병렬 번역)
merge_tr.py → tr_merged.json
```

- 롬 주소순으로 정렬해 배치를 만들어 **문맥 지역성** 확보
- 각 항목에 인접 문자열(`ctx`)을 붙여 번역자가 상황을 알 수 있게 함
- `field`/`inline` 은 바이트 상한(`limit`)을 함께 전달
- 용어집(`glossary.json`)에 게임 용어·한자 독음표·두음법칙표를 담아 일관성 유지
- 번역 지침은 [`tools/TRANSLATE_INSTRUCTIONS.md`](../tools/TRANSLATE_INSTRUCTIONS.md)

## 4. 기계 검증

```
validate2.py → issues.json
```

검사 항목:

| 검사 | 내용 |
|---|---|
| `fmt` | `%s %d %2d` 개수·순서가 원문과 같은가 |
| `gaiji` | `{G00}` 토큰이 보존됐는가 |
| `badchar` | 게임 폰트에 없는 문자가 섞였는가 |
| `jp-remains` | 일본어 한자·가나가 남았는가 |
| `limit` | 고정 필드 바이트 상한을 지켰는가 |
| `count` | 시퀀스 멤버 수가 원문과 같은가 |

발견된 문제와 처리:

- **가운뎃점 `·`(U+00B7)** 15건 → 인코더에서 `・`(U+30FB)로 정규화
- **반각 가나** → 인코더에 1바이트 인코딩 경로 추가
- **남은 일본 한자** → 해당 슬롯이 한글로 재활용되므로 그대로 두면 엉뚱한 글자가 나옴.
  실제 문장 1건은 수정, 바이너리 조각 9건은 원본 바이트 보존

## 5. 안전성 분석

번역보다 오히려 여기에 공이 많이 들었습니다.

### 포인터 진위 역추적 (`ptr_confirm.py`)

재배치하려면 포인터를 고쳐야 하는데, **가짜 포인터를 고치면 게임이 깨집니다.**
그래서 2,765개 참조를 전부 분류했습니다.

| 판정 근거 | 개수 |
|---|---|
| 포인터 배열 소속 (이웃 워드도 유효 포인터) | 2,159 |
| Thumb `LDR Rd,[PC,#imm]` 리터럴 풀 역추적 성공 | 585 |
| **미확인** | 21 |

미확인 21개는 **재배치 금지**로 표시해, 포인터를 건드리지 않는 제자리 기록만 허용했습니다.

### 겹침 엔트리 해소

추출기가 문자열 중간을 새 문자열로 오인한 경우가 9건 있었습니다
(예: `め、完全に我々を無視するとは許せぬ` 안의 `は許せぬ`).
둘 다 쓰면 서로 덮어쓰므로 우선순위를 정했습니다.

```
검증된 포인터가 가리키는 문자열  >  포인터 없는 문자열  >  미검증 참조
동급이면 긴 쪽
```

### DB 필드 침범 검사 (`field_check.py`)

고정 길이 레코드에 원문보다 긴 한글을 쓰면 다음 필드를 망칩니다.
확인 결과 원문보다 커진 필드는 **5건뿐이고 전부 2바이트**, 모두 원본이 0이던
패딩 안에서 끝나 다음 엔트리에 닿지 않았습니다.

## 6. 주입

```
inject.py → Nobunaga no Yabou (Korean).gba
```

1. 번역문에서 쓰인 한글 음절을 모아 **787자** 확정
2. 슬롯 배정 — 히라가나 슬롯(71개)에 고빈도 음절을 가나다순으로,
   나머지는 한자·가타카나 슬롯에
3. 갈무리11 BDF에서 12×12 비트맵을 뽑아 슬롯에 기록
   (베이스라인 ascent=14 기준이므로 위로 3px 시프트, ink 기준 수평 중앙 정렬)
4. 텍스트 인코딩 후 기록
   - 제자리에 들어가면 제자리 (5,753건)
   - 넘치고 재배치 가능하면 `0x33A1A0` 이후 여유 공간으로 이동 + 포인터 갱신 (1,354건)
   - 넘치는데 재배치 불가면 용량에 맞게 축약 (0건 — 사전에 짧은 번역으로 교체)

## 되짚어 보는 함정

| 함정 | 대응 |
|---|---|
| 폰트를 정적 분석으로 찾으려다 시간 소모 | 에뮬레이터 VRAM에서 글리프를 뽑아 롬을 역검색하는 편이 확실 |
| 타일맵을 폰트로 오인 (홀수 바이트가 전부 0) | 실제 바이트를 직접 눈으로 확인 |
| 번역문에 일본 한자가 남으면 다른 글자로 출력 | 주입 전 필수 검사 항목 |
| 가짜 포인터를 고쳐 게임이 깨질 위험 | 리터럴 풀 역추적으로 진위 판정, 미확인은 재배치 제외 |
| 문자열 겹침 오검출 | 검증된 참조 우선 정책으로 하나만 채택 |
| 고정 필드에 긴 번역을 넣어 다음 필드 파손 | slack 범위 내로 제한 + 침범 검사 |
