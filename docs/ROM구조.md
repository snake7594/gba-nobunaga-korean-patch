# 노부나가의 야망 (GBA) 롬 구조 분석

`Nobunaga no Yabou (Japan).gba` / 게임 코드 `ANBJ` / 메이커 `C8` (KOEI) / 4 MB
유효 데이터는 `0x33A198` 까지이고 그 뒤는 전부 0 패딩입니다.

---

## 1. 폰트를 찾아낸 과정

정적 분석만으로는 폰트를 찾지 못했습니다. 시도한 것과 결과는 다음과 같습니다.

| 방법 | 결과 |
|---|---|
| 비트 밀도 스캔 | 후보 구간 16개 — 전부 오답 |
| 글리프 셀 주기 자동 검출 | `0x10C000` 대의 16비트 타일맵을 오검출 |
| LZ77 압축 블록 스캔 | **0개** — 이 롬은 압축을 쓰지 않음 |
| 「一」형 글리프(가로줄 하나) 패턴 검색 | 후보 4개 — 전부 오답 |
| 1bpp/2bpp 시각 덤프 | 폰트 아님 |

결국 **동적 분석**으로 해결했습니다.

1. mGBA를 GDB 스텁과 함께 실행하고 모드 선택 화면까지 진행
2. GDB RSP로 VRAM 96 KB / 팔레트 / OAM / IO 레지스터 덤프
3. `DISPCNT`·`BGnCNT`를 해석해 BG3 레이어를 렌더 → `入門モード` 텍스트 확보
4. 화면에서 글리프 비트맵을 픽셀 단위로 추출
5. 그 비트맵을 **7가지 인코딩 가설**(2바이트/행 좌·우정렬 × BE/LE, 12비트 팩, 미러)로
   바이트열을 만들어 롬 전체를 검색

→ `packed12`(12비트 패킹, 글리프당 18바이트) 가설이 정확히 일치.
`入`은 `0x30B454`, `モ`는 `0x306096` 에서 발견되었고,
역산하여 폰트 시작 주소 **`0x305274`** 를 확정했습니다.

> **교훈**: 비정형 폰트 포맷은 정적 추론보다 *화면에 뜬 글리프를 그대로 검색*하는 쪽이 빠르고 확실합니다.

## 2. 폰트 포맷

```
주소  = 0x305274 + slot × 18
크기  = 18바이트 = 144비트 = 12행 × 12비트
비트  = MSB first, 행 단위 연속 (행 경계가 바이트 경계와 어긋남)
```

디코드 예 (Python):

```python
bits = int.from_bytes(rom[off:off+18], "big")
for y in range(12):
    row = (bits >> (144 - 12*(y+1))) & 0xFFF   # 12비트
    for x in range(12):
        pixel = (row >> (11-x)) & 1
```

부수적으로 **ASCII 폰트**가 `0x304DF4` 에 따로 있습니다 (8×12, 12바이트/자, 96자, 테이블 `0x30D604`).

## 3. 문자 매핑 테이블

`0x30D6CE` 부터 **u16 리틀엔디언 SJIS 코드가 오름차순으로 1,869개** 있습니다.
슬롯 인덱스가 곧 배열 첨자입니다.

| 구간 | 내용 | 개수 |
|---|---|---|
| 0 ~ 2 | `　`(전각공백) 등 | 3 |
| 3 ~ 217 | 기호 · 전각숫자 · 전각영문 · 히라가나 · 가타카나 | 215 |
| 218 ~ 1850 | 한자 | **1,633** |
| 1851 ~ 1868 | 가이지(외자, 유효한 SJIS 아님) | 18 |

분류하면 한자 1,633 / 가타카나 78 / 히라가나 71 / 기호 69 / 가이지 18 입니다.

### 렌더러

`0x08003620` 의 함수가 전형적인 이진 탐색입니다.

```asm
08003620: push {r4,r5,r6,lr}
08003626: movs r4, #0            ; lo = 0
08003628: ldr  r3, [pc, #0xc]    ; hi = 1868
0800362a: ldr  r5, [pc, #0x10]   ; table = 0x0830D6CE
0800362c: ldr  r6, [pc, #0x10]   ; font  = 0x08305274
08003644: adds r0, r4, r3
08003646: asrs r1, r0, #1        ; mid = (lo+hi)/2
0800364c: ldrh r0, [r0]          ; table[mid]
0800364e: cmp  r2, r0            ; 찾는 SJIS 코드와 비교
08003652: lsls r0, r1, #3        ; mid*8
08003654: adds r0, r0, r1        ; mid*9
08003656: lsls r0, r0, #1        ; mid*18   ← 글리프 크기 확정
08003658: adds r0, r0, r6        ; + 폰트 베이스
```

`mid*8 + mid = mid*9`, `<<1` 해서 `mid*18` — 여기서 글리프가 18바이트임이 코드로도 확인됩니다.

## 4. 텍스트 배치

텍스트는 **평문 Shift-JIS**, 널 종단입니다. 크게 세 종류입니다.

| 종류 | 위치 | 접근 방식 | 개수 |
|---|---|---|---|
| `ptr` | `0x220000`~`0x260000` 등 | 포인터(`0x08xxxxxx`)로 참조 | 2,559 |
| `field` | `0x30E56A`~`0x33A200` | DB 레코드 내 고정 필드 | 4,785 |
| `inline` | 텍스트 영역 | 포인터 없이 인접 배치 | 75 |

- 대사·메뉴는 대부분 `ptr`
- 무장/성/구니 이름은 `field` (레코드 스트라이드 7, 37, 24, 25, 80바이트 등)
- 여러 문자열이 **하나의 화면을 이루는 시퀀스**로 묶여 있는 경우가 많습니다.
  포인터 배열에서 주소가 4씩 연속하는 런을 찾아 187개 그룹(1,479개 문자열)을 복원했습니다.

### 제어 코드

| 코드 | 의미 |
|---|---|
| `0x0A` | 줄바꿈 |
| `%s` `%d` `%2d` `%4d` | 런타임 치환 (이름·수치) |
| SJIS `0xEBxx` 대역 일부 | 가이지 18자 — 도구에서는 `{G00}`~`{G17}` 로 토큰화 |

## 5. 그 밖에 확인된 것

| 주소 | 내용 |
|---|---|
| `0x10C000` ~ `0x12D000` | 16비트 타일맵 (홀수 바이트가 전부 0이라 폰트로 오인하기 쉬움) |
| `0x23AC00` ~ | 4bpp 타일 그래픽 |
| `0x2F0000` ~ | 스크립트/바이트코드로 보이는 데이터 |
| `0x310000` ~ | 포인터 테이블 (`0x0822Exxx` 대역을 가리킴) |
| `0x320000` ~ | 다기(茶器) 등 아이템 DB — SJIS 이름 포함 |
| `0x330000` ~ | 무장 DB (이름 + 능력치 + 카나 읽기) |
